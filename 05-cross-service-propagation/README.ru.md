# 05 · Контекст трассировки между HTTP-сервисами

[English](README.md) | [Русский](README.ru.md)

Английская версия — оригинал. Русский перевод поддерживается рядом с ней.

Gateway вызывает inventory: входящий серверный спан → бизнес-спан → исходящий
клиентский спан → серверный спан downstream. Контекст в памяти сам не пересекает
сеть: HTTP transport должен записать заголовки propagation.

## Наблюдение за сломанным примером

```sh
go run .
```

Gateway слушает 8080, inventory — 8081. В другом терминале
(`curl.exe` в Windows PowerShell):

```sh
curl -i http://localhost:8080/checkout
```

Оба сервера используют `otelhttp.NewHandler`, но у gateway обычный `http.Client`.
Inventory пишет в лог пустой `traceparent` и создаёт другой TraceID.
Для простоты два сервера работают в одном процессе, но общаются через HTTP:
граница передачи контекста настоящая.

## Исправление упражнения

Измените `ReserveInventory` в [exercise.go](exercise.go). Сохраните бизнес-спан
и контекст вызывающего кода, инструментируйте исходящий transport.

```sh
go test .
go test -tags=solution .
```

Первая команда изначально падает, вторая выбирает [solution.go](solution.go).
Тест использует `httptest.Server` и не требует свободных 8080/8081.
Он проверяет общий TraceID, наличие клиентского спана и то, что именно он стал
родителем downstream-спана. В [helper](helper.go) разобраны копирование клиента,
контекст запроса и освобождение тела ответа.

Демонстрация `go run .` остаётся сломанной после исправления упражнения.
Вернитесь к [контексту внутри процесса](../03-internal-context-propagation/README.ru.md),
чтобы отделить владение контекстом от его передачи по сети.
