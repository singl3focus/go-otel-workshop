# Жизненный цикл пула: приём, отмена и завершение

[English](README.md) | [Русский](README.ru.md)

Английская версия — оригинал. Русский перевод поддерживается рядом с ней.

Этот конечный пример расширяет [небольшой worker pool](../worker-pool-context/README.ru.md):
ограниченная очередь, явный отказ, HTTP I/O с учётом контекста, таймауты задач
и завершение воркеров до остановки трассировки. Он сам запускает loopback
HTTP-сервер на временном порту и сам завершается.
Docker, фиксированный порт и внешний сервис не нужны.

## Три сценария запуска

Из этого каталога:

```sh
go run . -mode=drain
go run . -mode=timeout
go run . -mode=cancel
```

В каждом запуске один воркер и одно место ожидания. Первая задача начинает
downstream HTTP, вторая ждёт, третья сразу получает отказ queue-full.
Затем приём закрывается, новая отправка получает отказ closed. Спан исходного
запроса завершается, его контекст отменяется до остановки пула.

| Режим | Как останавливается работа | Итог |
| --- | --- | --- |
| `drain` | Downstream разблокируется, обе принятые задачи завершаются | `accepted=2 completed=2 failed=0 queue_full=1` |
| `timeout` | Downstream ждёт отмены запроса; каждая задача достигает своего таймаута | `accepted=2 completed=0 failed=2 queue_full=1` |
| `cancel` | Бюджет ожидания уже отменён; пул прерывает активное I/O и отменяет ожидающую задачу | `accepted=2 completed=0 failed=2 queue_full=1` |

В каждой итоговой строке также есть `after_close=closed`. Затем batch exporter
выводит JSON: `demo.run`, `request.enqueue` и два `worker.process` в одной трассе.
Родитель воркеров — `request.enqueue`, новый фоновый корень не создаётся.
`job.outcome` равен `completed`, `deadline` или `canceled`. Ошибочные задачи
имеют событие исключения и Error, успешные сохраняют Unset.
У третьей отклонённой задачи нет спана воркера: её не приняли в обработку.

## Что разделено в коде

- **Приём:** `Submit` проверяет отмену запроса до приёма и не ждёт места
  в очереди. Queue-full и pool-closed — разные ошибки. Если задача уже принята,
  последующая отмена запроса не отзывает её.
- **Trace values:** задание хранит ID задачи и `trace.SpanContext`, а не контекст
  запроса. Воркер восстанавливает родителя поверх контекста жизни пула.
- **Бюджет задачи:** `WithTimeout` начинается при извлечении из очереди.
  Время ожидания не включено; если требуется общий deadline, передавайте его в задании.
- **I/O:** `http.NewRequestWithContext` переносит бюджет в настоящий `Client.Do`.
  Downstream handler ждёт свой request context. I/O не подменяется обычным sleep.
- **Остановка:** `Close` прекращает приём и закрывает очередь. `Shutdown` сначала
  дожидается принятых задач. Если бюджет истёк, отменяет I/O пула и ждёт выхода
  всех воркеров. Только затем пример завершает корневой спан и останавливает OTel.

`Submit` и `Close` используют общий mutex. Отправка под блокировкой неблокирующая,
поэтому конкурентный close не пересекается с отправкой в закрытый канал.
Заполненная очередь при этом даёт явный результат перегрузки.

## Границы примера

Отмена совместная. После истечения бюджета `Shutdown` продолжает ждать воркеров:
он не обещает жёсткий срок возврата, если собственный HTTP transport игнорирует
контекст. Показанный transport учитывает отмену. Выбран полный выход воркеров
до остановки телеметрии. Рабочему сервису также нужна общая политика завершения
процесса при неисправной зависимости.

Задачи хранятся только в памяти: падение процесса теряет очередь. Нет повторов,
постоянного хранилища, HTTP-endpoint постановки и исходящих клиентских спанов.
Loopback-вызов показывает отмену, а сетевую трассировку разбирает
[модуль 05](../../05-cross-service-propagation/README.ru.md).
В пуле с HTTP-входом преобразуйте перегрузку в подходящий ответ, например 503,
прекратите приём запросов, дождитесь handler и затем обработайте остаток очереди.

## Проверка

```sh
go test -race -count=1 -timeout=30s .
```

Тесты согласуют порядок через каналы, а не задержки sleep. Проверяются лимит
приёма, ID родителя, независимость от запроса, настоящая отмена HTTP по deadline,
отмена очереди, совместные Submit/Close и завершение спанов до shutdown провайдера.
Тест deadline использует реальный таймер; остальной порядок задаётся явно.

Источники: [контекст Request](https://pkg.go.dev/net/http#Request.Context),
[CancelFunc](https://pkg.go.dev/context#CancelFunc),
[Server.Shutdown](https://pkg.go.dev/net/http#Server.Shutdown).
