# Отделённый фоновый контекст

[English](detached-background-context.md) | [Русский](detached-background-context.ru.md)

Английская версия — оригинал. Русский перевод поддерживается рядом с ней.

[Запускаемый пример](../../03-internal-context-propagation/detached-background-context/README.ru.md)
сравнивает контекст запроса с фоном, у которого собственное ограничение времени.

## Время жизни запроса и операции

Контекст входящего HTTP-запроса отменяется при закрытии клиентского соединения,
отмене запроса (HTTP/2) или возврате `ServeHTTP`. Не считайте каждый серверный
таймаут общим таймаутом контекста: deadlines чтения/записи и отмена handler
имеют разное поведение.

Ответ 202 не продлевает жизнь контекста запроса для работы в очереди.
HTTP/DB/RPC-клиент, учитывающий контекст, может вернуть отмену при получении
старого контекста. `time.Sleep` игнорирует отмену и скрывает проблему в демонстрации.

## Отмена не удаляет родителя трассы

`SpanContext` — значение, доступное через контекст. Отмена не стирает TraceID/SpanID.
Записывающий потомок всё ещё может создаваться, дополняться, завершаться
и экспортироваться, а downstream-работа с тем же контекстом — падать.
Жизнью спана управляет End, а не отмена контекста, с которым его создали.

Поэтому `/bad` показывает корректно связанный `background.bad` с событием
исключения и статусом Error. Ошибка возникает в имитируемой downstream-операции,
а не доказывает потерю родителя в SDK.

## У независимой работы должен быть владелец

`context.WithoutCancel` сохраняет values, убирая deadline и отмену родителя.
Добавьте ограниченное время и отдайте отмену горутине, выполняющей работу:

```go
func (a *app) handleGood(w http.ResponseWriter, r *http.Request) {
    bg := context.WithoutCancel(r.Context())
    bg, cancel := context.WithTimeout(bg, 2*time.Second)
    go func() {
        defer cancel()
        ctx, span := a.tracer.Start(bg, "background.good")
        defer span.End()
        if err := simulateDownstreamCall(ctx); err != nil {
            span.RecordError(err)
            span.SetStatus(codes.Error, "background operation failed")
        }
    }()
    w.WriteHeader(http.StatusAccepted)
}
```

`defer cancel()` в handler активно отменит `bg` при возврате. Он не только
освобождает таймер. Внутри горутины defer позволяет работе завершиться
или достичь собственного deadline. Контекст не убивает горутину:
downstream-операции должны учитывать отмену.
В рабочем приложении также привяжите остановку воркеров к жизни приложения
и дождитесь их до shutdown трассировки. WithoutCancel убирает исходную отмену
целиком, включая сигнал остановки, если он передавался через родителя.

## Выберите нужные values и связь трасс

| Подход | Связь трасс | Values и отмена |
| --- | --- | --- |
| Контекст запроса | Та же трасса | Values и отмена запроса сохраняются |
| WithoutCancel и свой таймаут | Та же трасса | Все values, независимый таймаут |
| SpanContext в задании и новый контекст | По умолчанию та же трасса | Только явные данные задания и ID родительского спана |
| Новый корень с `trace.Link` | Отдельная связанная трасса | Явная модель независимо управляемой операции |
| Inject/Extract через carrier | Зависит от старта потребителя | Подходит для сериализованного сообщения и границы процесса |

[Worker pool](../../03-internal-context-propagation/worker-pool-context/README.ru.md)
передаёт в задании только SpanContext. Воркер вызывает
`trace.ContextWithSpanContext(context.Background(), job.parent)` и добавляет
свой таймаут. Так произвольные values запроса намеренно не удерживаются.
Если все воркеры завершаются до возврата синхронного родителя, обычная передача
контекста уместна, как в [прогреве кэша](../../04-non-standard-cases/cache-warmup/README.ru.md).

## Время спанов и propagation

Потомок может начаться или закончиться после завершения родителя. Связь
parent/child логическая и не требует вложенности временных интервалов.
Выбирайте link, если отдельная трасса точнее отражает владение операцией,
а не только ради аккуратной временной диаграммы.

Сохранение values также оставляет активный спан доступным инструментации,
записывающей HTTP-заголовки. Сам WithoutCancel не передаёт контекст по сети:
исходящий transport или явный propagator всё ещё должен записать `traceparent`.

## Вопросы для ревью

- Должна ли задача пережить HTTP-ответ и кто дожидается её при остановке?
- Учитывают ли операции воркера отмену или там только обычный sleep?
- Вызывает ли cancel владелец фоновой работы и ограничено ли её время?
- Нужны ли все values запроса или достаточно данных задания и SpanContext?
- Отменяет ли тест исходный запрос после ответа и проверяет ли завершение
  работы вместе со связью с родителем?
